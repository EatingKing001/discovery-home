# 多人并行修改安全流程

本文用于降低多个代理或开发者同时修改静态原型时的覆盖风险。所有参与者共享同一工作区时，开始和交付前都要重新检查文件状态。

## 可以直接并行的范围

满足以下条件的不同模块目录通常可以并行：

- 每个任务只修改自己的 `tabs/<module-id>/`。
- 不同时修改 shell、公共 CSS、共享 JS 或共享资源。
- 不依赖对方尚未落盘的 DOM、路由或协议变更。

## 需要先协调的范围

以下文件或目录属于高冲突区域：

- `index.html`
- `shared/css/`
- `shared/js/`
- `shared/assets/` 中已有公共资源
- `design-system/` 中的公共规范示例
- `docs/` 中的架构和归属地图

修改这些区域前，要声明文件范围、消费者和预计验证方式。同一时间尽量只由一个任务拥有同一个高冲突文件。

## 模块内修改规则

模块任务优先限定在：

```text
tabs/<module-id>/index.html
tabs/<module-id>/<module-id>.css
tabs/<module-id>/<module-id>.js
tabs/<module-id>/assets/
```

如果模块需要新的公共能力，先在模块内实现和验证；达到公共化门槛后再单独安排提升任务。

## 公共化门槛

从模块中提炼的组件、布局模式或交互能力，只有两个及以上产品模块已经真实使用、形态稳定、消费者清晰并且 Design System 可核对时，才提升到 `shared/`。

## 推荐工作顺序

1. 开始前检查当前路径、Git 状态和已有未提交改动；未初始化 Git 时记录这一事实。
2. 阅读 `AGENTS.md`、`README.md` 和与任务相关的归属地图。
3. 声明本任务的文件范围，避开他人正在修改的文件。
4. 先完成模块内实现，再处理确有必要的公共改动。
5. 执行与影响范围相称的静态、资源和浏览器验证。
6. 交付前重新检查差异，只总结本任务实际修改。

## 停止并询问

出现以下情况时，不应自行扩大修改范围：

- 需要覆盖或删除来源不明的既有改动。
- 模块与 shell 对同一 DOM、路由或交互的所有权不清楚。
- 新公共规则会改变多个未纳入验证的页面。
- 资源归属无法判断，或必须移动/删除共享资源。
- 需要回退版本，但用户尚未确认具体提交和范围。
